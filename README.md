# ⚡ GridSense AI — Cloud & DevOps Edition

AI-powered smart-grid monitoring and fault localization, extended with a production-style container and cloud delivery workflow.

GridSense monitors substations, feeders, transformers, poles and telemetry. Its fault-localization engine processes telemetry events, identifies a likely fault segment, creates incidents and updates the operator dashboard in real time.

This edition keeps the original React + Node.js + MongoDB application and adds Docker, Nginx, Jenkins CI/CD, Terraform-managed AWS infrastructure, and Prometheus/Grafana monitoring.

## 1. Application features

- JWT-based login and protected APIs
- Live grid KPIs, incidents, alerts and analytics
- Interactive map for substations, feeders, transformers and poles
- Telemetry processing for voltage, battery, signal, heartbeat, power-loss and power-restore events
- Fault localization, incident grouping and restoration detection
- Incident timeline, severity, confidence and affected-house estimates
- Fault simulator for pole, feeder and transformer failures
- MongoDB persistence and Socket.IO connectivity

## 3. Architecture

### Application request flow

```text
Browser
  |
  v
Nginx :80  (React static files + reverse proxy)
  |                           | /api/*                   \ /socket.io/*
  v                           v
Express / Node.js API :5000 + Socket.IO
  |
  v
MongoDB :27017
```

Only Nginx publishes the application port. The API and MongoDB stay on the private Docker bridge network.

### Cloud deployment flow

```text
Developer

   v
Jenkins EC2
```

Terraform creates the VPC networking, security groups, EC2 instances, Elastic IPs, SSH deployment key and initial server configuration.

## 5. Run locally

### Prerequisites

- Node.js 22 or later
- Docker Desktop with Docker Compose
- Git

### Start the full application with Docker

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Edit `.env` and set strong, unique values for `JWT_SECRET` and `GRAFANA_PASSWORD`. Keep `FRONTEND_ORIGIN=http://localhost,http://localhost:3000` for local Docker/Vite. The Jenkins deployment stage updates the EC2 `.env` to the app public URL generated by Terraform. If you use a custom domain, update `FRONTEND_ORIGIN` to that exact origin.

```powershell
docker compose up --build -d
docker compose ps
docker compose logs -f
```

Open:

- Application: http://localhost
- Application health: http://localhost/health

The API and database are not published to the host. Nginx proxies `/api` and `/socket.io` to the backend.

To stop:

```powershell
docker compose down
```

To stop and delete the local database and monitoring data:

```powershell
docker compose down -v
```

### Run without Docker (development)

Start MongoDB locally, then in PowerShell:

```powershell
cd backend
Copy-Item ..\.env.example .env
# Set MONGO_URI=mongodb://127.0.0.1:27017/gridsense-ai in backend/.env
npm install
npm run dev
```

In a second terminal:

```powershell
cd frontend
Copy-Item .env.example .env
npm install
npm run dev
```

Keep `.env` files out of Git.

## 6. Docker details

- `backend/Dockerfile`: builds a small Node.js production image, installs production dependencies and runs as the non-root `node` user.
- `frontend/Dockerfile`: multi-stage build. Node/Vite compiles React assets; Nginx serves the static build.
- `frontend/nginx.conf`: serves the SPA and reverse-proxies API and Socket.IO requests.
- `docker-compose.yml`: runs the API, web server and MongoDB; named volumes persist database data.
- Health checks ensure MongoDB and the API are ready before dependent containers start.

## 7. Jenkins CI/CD

The root `Jenkinsfile` implements:

1. Checkout the latest GitHub commit.
2. Pre-flight checks for Docker and deployment configuration.
3. Run backend integration tests.
4. Build versioned API and frontend Docker images.
5. Transfer images to the application EC2 over SSH.
6. Copy Compose and monitoring configuration.
7. Deploy using Docker Compose.
8. Run a smoke test against `/health`.

The pipeline polls the Git repository every five minutes. A GitHub webhook can be configured for faster triggering.

### Jenkins job setup

1. Open the Jenkins URL printed by Terraform.
2. Retrieve the initial password using the command printed in Terraform outputs.
3. Install the suggested plugins and create an administrator.
4. Select **New Item → Pipeline**.
5. Under Pipeline, choose **Pipeline script from SCM**.
6. Select Git and enter this repository's HTTPS URL.
7. Set branch to `*/main` and script path to `Jenkinsfile`.
8. Save and select **Build Now**.

The Jenkins EC2 bootstrap installs Java, Jenkins, Docker, Docker Compose and Node.js. Terraform creates the restricted SSH deployment key and Jenkins deployment environment file.

## 8. AWS infrastructure with Terraform

### Resources created

| Resource | Purpose |
|---|---|
| VPC `10.0.0.0/16` | Isolated cloud network |
| 2 public subnets | App and Jenkins EC2 instances across two AZs |
| 2 private subnets | Reserved for future private managed services |
| Internet Gateway + public route table | Internet connectivity for public instances |
| App security group | HTTP/HTTPS, restricted SSH and restricted monitoring UI |
| Jenkins security group | Jenkins UI and administrator SSH |
| App EC2 | Docker Compose application host |
| Jenkins EC2 | CI/CD controller and Docker image builder |
| Elastic IPs | Stable public addresses |
| Encrypted gp3 EBS volumes | Persistent server storage |
| Terraform-generated SSH key | Jenkins-to-app deployment access |

The current deployment keeps MongoDB in a persistent Docker volume on the application EC2. For a larger production deployment, move the database to MongoDB Atlas or a managed database service and configure backups.

### Prerequisites

- AWS account
- AWS CLI configured with an IAM identity that can create the listed resources
- Terraform 1.5+
- An SSH key pair

### Step 1: Create an SSH key on Windows

If you do not already have a key:

```powershell
ssh-keygen -t ed25519 -C "gridsense-admin"
```

The public key is normally at:

```text
C:\Users\YOUR_USER\.ssh\id_ed25519.pub
```

Display it:

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
```

Copy the complete public key line.

### Step 2: Configure Terraform

```powershell
cd terraform
Copy-Item terraform.tfvars.example terraform.tfvars
notepad terraform.tfvars
```

Set:

- `admin_cidr`: your current public IP followed by `/32`
- `jenkins_allowed_cidr`: your current public IP followed by `/32`
- `admin_public_key`: the public SSH key line
- `aws_region`: your preferred AWS region

Do not use `0.0.0.0/0` for SSH or the Jenkins UI.

### Step 3: Provision AWS

```powershell
terraform init
terraform fmt -recursive
terraform validate
terraform plan
terraform apply
```

Review the plan and type `yes` only when you are ready to create billable resources.

Terraform outputs the application URL, Jenkins URL, SSH commands and a command to retrieve Jenkins's initial password.

The first boot can take several minutes. Check `/var/log/cloud-init-output.log` on an instance if its software installation is not complete.

### Step 4: Configure Jenkins

Follow the Jenkins job setup above. Use your actual GitHub repository URL and the `main` branch.

### Step 5: Verify deployment

- Open the application URL.
- Open `/health` and confirm it returns HTTP 200.
- Check the Jenkins build stages.
- On the app instance, run `docker compose ps` and `docker compose logs -f`.

### Step 6: Monitoring

The Jenkins deployment starts the monitoring profile too:

- Prometheus: `http://APP_PUBLIC_IP:9090`
- Grafana: `http://APP_PUBLIC_IP:3001`

Both web interfaces are restricted by the app security group to `admin_cidr`. The Grafana password is generated by Terraform and stored as a sensitive Terraform output.

Prometheus scrapes:
- Node Exporter for host-level CPU, memory, disk and network metrics.
- cAdvisor for container resource metrics.
- Prometheus itself.

### Step 7: Clean up AWS resources

When you finish demonstrating the project:

```powershell
cd terraform
terraform destroy
```

Review the destroy plan and type `yes`. This removes the provisioned AWS infrastructure. Download anything you need from the instances first.

## 9. Network and security

| Port | Service | Access |
|---|---|---|
| 80 | Nginx / application | Public |
| 443 | Reserved for future HTTPS | Public security-group rule; TLS is not configured yet |
| 5000 | Node.js API | Docker network only |
| 27017 | MongoDB | Docker network only |
| 8080 | Jenkins | Configured administrator CIDR only |
| 22 | SSH | Administrator CIDR; Jenkins-to-app also allowed |
| 9090 | Prometheus UI | Configured administrator CIDR only |
| 3001 | Grafana UI | Configured administrator CIDR only |
| 9100 | Node Exporter | Docker network only |
| 8080 (container network) | cAdvisor metrics | Docker network only |

Security practices included:

- `JWT_SECRET` is required before the authentication routes load; there is no hardcoded fallback secret.
- The frontend uses a same-origin `/api` path by default in Docker/production. For local Vite development, set `VITE_API_URL=http://localhost:5000` in `frontend/.env`.
- Terraform generates unique application and Grafana secrets.
- EC2 requires IMDSv2.
- EBS root volumes are encrypted.
- MongoDB and the Node.js API are not directly exposed to the Internet.
- SSH and Jenkins UI access are restricted to the configured administrator CIDR.
- Backend container runs as a non-root user.
- Real `.env`, SSH private keys and Terraform state are excluded from Git.

**Important:** Terraform state and EC2 user data contain sensitive deployment material. Keep the state file private and never commit it. For a production system, move secrets into AWS Secrets Manager or Systems Manager Parameter Store, add HTTPS with a managed certificate, configure database backups, and use a hardened remote Terraform state backend.

```powershell

docker compose logs -f api
docker compose logs -f web
docker compose logs -f mongo
```

On the application EC2:

```bash
cd /opt/gridsense
sudo docker compose ps
sudo docker compose logs -f
sudo docker compose --profile monitoring ps
```

If the application does not become healthy, check the API logs, MongoDB health, environment file and security group rules.
